# P3 - Outward

Backend: `models/store_outward.py`, `services/store_outward.py`, `routers/store_outward.py`, `documents/store/outward_forms.py`.
Frontend: `features/store/outward/`. Tests: `backend/tests/store/test_p3_outward.py`.
Tables (all new, made by `create_all`): `store_issue`, `store_issue_line`, `store_issue_return`, `store_issue_return_line`,
`store_writeoff_request`, `store_outward_log`.

## Documents

| Path key | Ledger `ref_doc_type` | Number | Moves stock when posted |
|---|---|---|---|
| `issue` | `ISSUE` | `ISSUE/CS01/26-27/00001` | `ISSUE_OUT` (site use) or `SUBCON_ISSUE_OUT` (to a subcontractor), valued at the store's average rate |
| `returns` | `ISSRET` | `ISSRET/...` | `ISSUE_RETURN_IN` / `SUBCON_RETURN_IN`, at the rate the line left at |

Lifecycle for both: `DRAFT -> SUBMITTED -> APPROVED -> POSTED`, or `CANCELLED` from any earlier state. Only POSTED touches stock; only a
DRAFT is edited or deleted; a POSTED document is immutable - cancel it (reversing its movements) and make a new one. Every change of
status is a row in `store_outward_log`. Posting is one transaction: if any line cannot move (insufficient stock, frozen store) nothing does
and the document keeps its status.

## Rights

`store.outward.view` reads. `.create` makes, edits, deletes drafts and **submits**. `.approve` approves. `.post` posts. `.cancel` cancels.
`.direct_issue` issues, approves and posts in one step (`POST /issue/direct`); it is a right of its own, so create and post are not enough.
A direct issue is marked `direct` on the document and has a `direct` row in the log. Staff only see and work in the stores they are assigned
to; another company's records answer 404.

## Rules worth knowing

* **Where the cost goes.** A site issue's every line is charged to **either** a BOQ item of the issue's project **or** one of the cost heads
  (`SITE_ESTABLISHMENT`, `P_AND_M_FUEL`, `OVERHEAD`, `SAFETY`, `TEMPORARY_WORKS`), never both and never neither. The ledger entry carries the
  project, work order, BOQ item and cost head, so the cost reports (P5) read them straight from it. A subcontractor issue may name neither.
* **Stock.** Submit checks what is on hand (lines of the same item add up) and says how much there is; post checks again inside the posting
  transaction, so stock used in between stops the post and leaves the document APPROVED.
* **Returnables.** An item whose settings category is `RETURNABLE` or `TOOL` needs a holder on the issue (an employee, a gang, or the
  subcontractor) and may carry an expected-return date (not before the issue date). `GET /returnables` lists what is still out with
  overdue days; `get_outstanding_returnables` is the cross-slice function.
* **Returns.** Only against a POSTED issue; at most what is still out, counting every live return. Each line says how much **came back**
  (goes into stock) and how much was **lost or damaged** (a reason is required). Only returnables can be lost - a consumable is used up.
  Lost quantity creates an OPEN `store_writeoff_request`; it counts as accounted for, so it stops being "out".
* **Cancelling.** An issue with a live return cannot be cancelled until the return is. Cancelling a posted return reverses its stock and
  withdraws its OPEN write-off requests; if one was already CLOSED the return cannot be cancelled.
* **Write-off requests.** `list_writeoff_requests(db, status)` returns every company's requests - callers filter by their own stores - and
  `close_writeoff_request(db, id, ref_doc_type, ref_doc_id, user_id)` marks one CLOSED by the document that dealt with it (404 if missing,
  409 if it is not OPEN). It flushes and does not commit.
* **Subcontractor recovery.** `get_subcon_issues(db, subcontractor_id, upto_date)` lists POSTED issues to the subcontractor. A line marked
  *chargeable* has a recovery rate (per base unit); recovery value = (issued - returned) x rate, so what is lost or never returned is still
  recovered. Dates cannot be in the future.

## API (`/api/store/outward`)

`GET ""` (latest issues); pickers `GET /pick/boq-items?project_id=`, `/pick/work-orders?project_id=`, `/pick/subcontractors`,
`/pick/employees`; `GET /issue-lines/{issue_id}`; `GET /returnables` (+ `/export`); `GET /writeoffs?status=`;
`GET /subcontractors/{id}/recovery?upto=`. For each kind (`issue`, `returns`): `GET /{kind}` (filters `status`, `store_id`, `q`, `project_id`,
`from_date`, `to_date`), `GET /{kind}/export` (Excel), `POST /{kind}`, `GET|PUT|DELETE /{kind}/{id}`, `GET /{kind}/{id}/print` (PDF),
`POST /{kind}/{id}/{submit|approve|post|cancel}` (cancel takes `{"reason"}`), and `POST /issue/direct`.

## Screens (`/store/hub/outward/...`)

Issues and Returns lists (status/store/search filters, Excel, New, and Direct issue for those who hold the right), the document page (lines,
history, action bar, print, Return material), the issue and return forms, and the Returnables out, Write-offs and Subcontractor recovery pages.
