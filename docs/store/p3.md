# P3 - Outward

Backend: `models/store_outward.py`, `services/store_outward.py`, `routers/store_outward.py`, `documents/store/outward_forms.py`.
Frontend: `features/store/outward/`. Tests: `backend/tests/store/test_p3_outward.py`.
Tables (all new, made by `create_all`): `store_indent`, `store_indent_line`, `store_issue`, `store_issue_line`, `store_issue_return`,
`store_issue_return_line`, `store_recovery`, `store_returnable_closure`, `store_writeoff_request`, `store_gate_pass`, `store_gate_pass_line`,
`store_outward_setting`, `store_outward_log`.

## What it holds

| Thing | Path key | Number | Stock |
|---|---|---|---|
| Material indent | `indent` | `INDENT/CS01/26-27/00001` | none |
| Issue slip (site or subcontractor) | `issue` | `ISSUE/...` | posted: `ISSUE_OUT` / `SUBCON_ISSUE_OUT` at the store's average rate |
| Return to store | `returns` | `ISSRET/...` | posted: `ISSUE_RETURN_IN` / `SUBCON_RETURN_IN` at the rate the line left at |
| Gate pass | `gate-pass` | `GATE/...` | none |

Issues and returns run `DRAFT -> SUBMITTED -> APPROVED -> POSTED`, or `CANCELLED`. Only POSTED touches stock; only a DRAFT is edited or deleted; a
POSTED document is immutable - cancel it (reversing its movements) and make a new one. Posting is one transaction: if any line cannot move
(insufficient stock, frozen store) nothing does. `InsufficientStockError` reaches the screen as a message that says what is on hand
("Only 5000.000 kg of Cement OPC on hand in this store; 5050.000 was asked for"). Every change of status is a row in `store_outward_log`.

## Rights

`store.outward.view` reads. `.create` makes, edits and deletes drafts, submits, makes indents, returns, gate passes and write-off requests. `.approve`
approves issues and returns, approves or closes an indent (see below), converts a returnable to a recovery and changes the settings. `.post` posts.
`.cancel` cancels (a posted document is reversed; also cancels gate passes and an approved indent). `.direct_issue` issues without an indent (and is the
right for the one-step `POST /issue/direct`). Staff only see and work in the stores they are assigned to; another company's records answer 404.

## Indents

A site engineer raises an indent: project, store, a work order and/or BOQ item and/or an activity, a required-by date and lines (item, quantity,
purpose). It runs `DRAFT -> SUBMITTED` (waiting for the approver) `-> OPEN` (approved, nothing issued) `-> PARTIAL -> CLOSED`, or `CANCELLED`.

* **Approval** is the project manager's: if the project names a manager only they (or `store.admin`, or the account holder) can approve; if it names none,
  any holder of `store.outward.approve` can. The approver sets an approved quantity per line - never more than was asked, possibly less; lines left out are approved as
  asked; cutting everything to nothing is refused (cancel instead).
* **Fulfilment** is read from POSTED issues: `fulfilled`, `pending = approved - fulfilled` per line. The status moves OPEN -> PARTIAL -> CLOSED as issues post and back
  as one is cancelled. **Close short** (`approve` right) closes an indent with quantity pending, and it stays closed. An indent with issues against it cannot be cancelled.
* Issuing against an indent: each issue line names the indent line it fills and may not take more than is still pending (submitted, approved and posted issues count;
  a draft reserves nothing and is checked again at submit and post). The cost goes where the indent said (its BOQ item) unless the line says otherwise.

## Issues

* **Without an indent a site issue needs `store.outward.direct_issue`** (it is marked `direct`); with an approved indent the create right is enough. A subcontractor issue
  is made against the subcontract work order, not an indent.
* Charged to a BOQ item of the project **or** a cost head (`SITE_ESTABLISHMENT`, `P_AND_M_FUEL`, `OVERHEAD`, `SAFETY`, `TEMPORARY_WORKS`), never both and never neither (a
  subcontractor issue may name neither). The ledger entry carries project, work order, BOQ item and cost head.
* **Who received it** is required: a PERSON (optionally an employee), a GANG or a FOREMAN, with a name.
* **A closed work order blocks issuing** (and indenting): status `Closed`, `Cancelled` or `Rejected`. Checked on save, submit and post.
* **Norm warning, never a block**: if the reports slice (P5) has a norm for the BOQ item and item, the issue shows a warning when what has been issued to that BOQ item (net of
  returns), with this issue, passes `get_theoretical_requirement`. Silent when there is no norm or the slice is not there.
* Stock is checked at submit (lines of an item add up) and again at post.

## Free issue to a subcontractor

Needs the subcontractor and their **subcontract work order** (their order, on the project, not cancelled/terminated/closed). Each line is **free of cost** or **chargeable**,
and a chargeable line's recovery rate is the **contract rate** (typed) or the **average cost** the stock left at (read at posting), **plus a handling %** - the line's own, or the
company's default (`GET/PUT /settings`: `subcon_handling_pct`, `default_recovery_basis`). Posting writes a `store_recovery` row per chargeable line with the resolved rate
(`recovery_rate = base x (1 + handling/100)`); returns take their quantity off it and cancelling the issue cancels it. `get_subcon_issues(db, subcontractor_id, upto_date)` reads
them: recovery value = (issued - returned) x rate for chargeable lines, nothing for free ones, and returnables converted to a charge are listed too (on the line they came from).

## Returns

Always against a POSTED issue line, valued at the rate it left at, never more than is still out (issued less what is returned, lost, converted or written off - counting every live
return). Each line gives what **came back** and what was **lost** (returnables only; a write-off request is raised for it). A returned line is **GOOD** or **DAMAGED**; damaged goods
must go into one of the store's bins (a reason is required) - they are stock again, kept apart by bin. Make a bin (e.g. `DAMAGED`) under Masters first.

## Returnables

Items whose settings category is `RETURNABLE` or `TOOL` need a holder (the person/gang/foreman who received them; a subcontractor issue's holder is the subcontractor) and may carry an
expected-return date. `GET /returnables` is the outstanding register with overdue days; `get_outstanding_returnables(db, project_id, store_id)` is the cross-slice function. Each
outstanding line is closed by **return**, by **conversion to a chargeable recovery** (`POST /returnables/{line}/convert`: quantity, rate, handling %, reason; needs `approve`; creates a
`CONVERSION` recovery against the holder), or by a **write-off request** (`POST /returnables/{line}/writeoff`: creates the OPEN request that P4 posts; this slice never posts a write-off).
`list_writeoff_requests` / `close_writeoff_request` are the contract functions. An issue with closures, a live return or a live gate pass cannot be cancelled.

## Gate passes

For material leaving the premises, made from a POSTED issue (all of it, or the lines and quantities named; the sum on live passes cannot exceed what was issued). A pass for returnable
items says when it is due back (given, else taken from the issue line) and shows overdue days; `close` marks the returnable material back; `cancel` needs the cancel right. No stock moves.

## API (`/api/store/outward`)

`GET ""`; pickers `/pick/boq-items`, `/pick/work-orders`, `/pick/subcontractors`, `/pick/employees`, `/pick/subcontract-orders`, `/pick/bins`; `GET /issue-lines/{id}`, `GET /indent-lines/{id}`;
`GET /returnables` (+ `/export`), `POST /returnables/{line}/convert|writeoff`; `GET /writeoffs`; `GET /recoveries`; `GET /subcontractors/{id}/recovery`; `GET|PUT /settings`.
Indents: `GET|POST /indent`, `GET|PUT|DELETE /indent/{id}`, `GET /indent/export`, `GET /indent/{id}/print`, `POST /indent/{id}/submit|approve|cancel|close`.
Gate passes: `GET|POST /gate-pass`, `GET /gate-pass/{id}`, `/print`, `/export`, `POST /gate-pass/{id}/close|cancel`.
Issues and returns: `GET /{kind}` (filters), `/export`, `POST /{kind}`, `GET|PUT|DELETE /{kind}/{id}`, `/{id}/print`, `POST /{kind}/{id}/{submit|approve|post|cancel}`, `POST /issue/direct`.

## Printables

Indent, issue slip (the subcontractor version is titled as the subcontractor material issue note and shows the recovery basis), returnable gate pass (and the plain outward gate pass),
return note (with condition and bin).

## Screens (`/store/hub/outward/...`)

Indents (list, form, page with the approval dialog, issue-against-it, close short, cancel), Issues and Returns (the issue form fills from an indent and asks who received it, the subcontract
order and the recovery basis; the return form asks for condition and the damaged bin), Gate passes, Returnables out (with Charge and Write off), Write-offs, Recoveries, Subcontractor
statement, Settings.
