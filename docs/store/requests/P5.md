# P5 requests

## To P2 (Inward): a published count of GRN lines waiting for QC

**What:** `store_inward.count_qc_pending(db, client_id, store_ids=None) -> int`, the GRN lines in QC_PENDING on GRNs
that are not cancelled.

**Why:** the Store dashboard shows "GRNs pending QC". P5 may not read `store_grn_line`, so until this exists the tile
shows "once Inward publishes it". P5's `store_integration.grns_pending_qc` will call it.

## To P3 (Outward): a published count of open indents

**What:** `store_outward.count_pending_indents(db, client_id, store_ids=None) -> int`, the indents approved and not yet
fully issued.

**Why:** the "Pending indents" dashboard tile, as above. It will be called from `store_integration.pending_indents`.

## To P3 / P4: how losses are posted

`get_project_material_cost` counts `WASTAGE_OUT`, `SCRAP_OUT` and `ADJUST_OUT` (less `ADJUST_IN`) as project cost,
charged by the entry's `project_id`.

- **P3 / P4:** a write-off should post `WASTAGE_OUT` with the project set.
- **P4:** a transit loss should post `ADJUST_OUT` (or `WASTAGE_OUT`) at the receiving store, with the project set and
  ref `TRANSFER`.

If you post them differently, tell P5.

## To P1 (ledger indexes): none needed now

The reports filter on store + item + date (`ix_store_ledger_store_item_date`), project + date
(`ix_store_ledger_project_date`) and movement type (indexed). If the registers get slow on a large ledger, P5 will ask
for `(store_id, movement_type, txn_date)`.

## To the lead

`app/services/store_integration.py` calls `store_inward.get_po_receipt_summary` (P2) and `store_outward` /
`store_control` (P3 / P4) at call time. Their stubs on master return empty results, so P5 runs before they merge.
After the merge, the E2E test's `slice_post` helper should be replaced by the real document flows.
