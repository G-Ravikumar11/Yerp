# P2 - Inward

Backend: `models/store_inward.py`, `services/store_inward.py`, `routers/store_inward.py`, `documents/store/inward_forms.py`.
Frontend: `features/store/inward/`. Tests: `backend/tests/store/test_p2_inward.py`.
Tables (all new, made by `create_all`): `store_grn`, `store_grn_line`, `store_purchase_return`, `store_purchase_return_line`,
`store_client_supply`, `store_client_supply_line`, `store_opening`, `store_opening_line`, `store_inward_log`.

## Documents

| Path key | Ledger `ref_doc_type` | Number | Moves stock when posted |
|---|---|---|---|
| `grn` goods receipt | `GRN` | `GRN/CS01/26-27/00001` | `GRN_IN` per accepted line, at the line's rate |
| `returns` purchase return | `PRTN` | `PRTN/...` | `PURCHASE_RETURN_OUT`, valued at the average |
| `client-supply` | `CSUP` | `CSUP/...` | `CLIENT_SUPPLY_IN`, at the client's rate (nil if none) |
| `opening` opening stock | `OSTK` movement `OPENING_IN`; ledger type `OSTK` | `OSTK/...` | `OPENING_IN` per line |

Lifecycle (every document): `DRAFT -> SUBMITTED -> APPROVED -> POSTED`, or `CANCELLED` from any earlier state. Only POSTED
touches stock. Only a DRAFT is edited or deleted; a POSTED one is immutable - cancel it (which reverses its movements with
`reverse_document`) and make a new one. Every change of status is a row in `store_inward_log` (who, when, from, to, note).
Posting is one transaction: if any line cannot move (insufficient stock, frozen store) nothing does and the document keeps
its status.

## Rights

`store.inward.view` reads. `.create` makes, edits, deletes drafts and **submits**. `.approve` approves and records the quality
check. `.post` posts. `.cancel` cancels. A member of staff only sees and works in the stores they are assigned to; another
company's documents answer 404.

## Rules worth knowing

* Quantities are typed in any of the item's units and stored in its **base unit** (`entry_uom`/`entry_qty` are kept too).
  A unit with no conversion is a 400 that names the item. Rates typed per entry unit are stored per base unit.
* **Against a purchase order**: the PO must be `Approved`; each line names a PO line (its `item_code` must be a stock item).
  The accepted total on a PO line may not exceed ordered x (1 + the item's over-receipt tolerance %), counting every
  submitted/approved/posted receipt. Checked on save, on submit and again on post.
* **Quality check**: an item with `qc_required` starts each GRN line `PENDING` with nothing accepted. `POST /grn/{id}/qc/{line}`
  records `PASSED` (optionally rejecting part, with a note) or `FAILED` (reject all, with a note). A receipt with a pending
  check cannot be submitted. Only accepted quantity enters stock. A receipt with nothing accepted cannot be posted.
* **Purchase return**: only from a POSTED receipt; at most the accepted quantity less what is already on live returns. A receipt
  with a live return cannot be cancelled until the return is.
* `get_po_receipt_summary(db, po_id)` (the cross-slice contract) counts POSTED receipts only, in base units; accepted is net of
  posted returns and pending is `max(0, ordered - accepted)`.
* Dates cannot be in the future.

## API (`/api/store/inward`)

`GET ""` (latest receipts), `GET /po-options`, `GET /po-summary/{po_id}`, `GET /grn-lines/{grn_id}`, and for each kind
(`grn`, `returns`, `client-supply`, `opening`): `GET /{kind}` (filters `status`, `store_id`, `q`, `from_date`, `to_date`),
`GET /{kind}/export` (Excel), `POST /{kind}`, `GET|PUT|DELETE /{kind}/{id}`, `GET /{kind}/{id}/print` (PDF),
`POST /{kind}/{id}/{submit|approve|post|cancel}` (cancel takes `{"reason"}`), `POST /grn/{id}/qc/{line_id}`.

## Screens (`/store/hub/inward/...`)

A list per kind with status/store/search filters and Excel, `new`, a document page (lines, history, the action bar, print,
the quality-check dialog), and `:id/edit` for drafts.
